# Chat-screening — Architecture Review & Refactor Plan

**Author:** Andrea Palladio
**Date:** 2026-05-25
**Status:** Draft for review by @PeterMust
**Scope:** Frontend (`app.js`, `index.html`, `config.js`). The Supabase backend (schema, RPCs, Edge Functions) is treated as a **fixed contract** for Phase 2 — out of scope for the rewrite. Phase 1 may extend backend RPC signatures where individual tickets require it.

## 0. TL;DR

The tool works in production but the frontend has accumulated structural debt. Direction agreed with Peter (2026-05-25):

1. **Phase 1 — Ship the 7 open chat-screening tickets** (#148, #149, #150, #151, #153, #154, #155) in the current vanilla codebase. **No architectural refactor here**; just user-visible fixes and features. Tag the result as the parity baseline. ~1.5–2 weeks.
2. **Phase 2 — Vue 3 rewrite** of the frontend on Vite + Vue 3 + TypeScript + Pinia against the same Supabase backend. Feature parity is defined as "Phase 1 baseline behaviour" (i.e. `FEATURES.md` + the seven shipped tickets). ~3 weeks.

This document maps current architecture (§1), catalogues the structural issues the rewrite will address (§2), and specifies what each phase delivers (§3). Decisions Peter needs to confirm before Phase 2 starts are in §6.

The backend (`supabase/`) is well-designed and reusable as-is. Structural issues are concentrated in the frontend monolith.

## 1. Current architecture

### 1.1 Top-level layout

A zero-build single-page application that loads three scripts directly:

```
index.html  (2,172 lines: ~1,800 of inline CSS in a <style> block + ~270 of DOM)
  ├── <script src=".../@supabase/supabase-js@2"> (CDN, jsdelivr)
  ├── <script src="config.js">                    (gitignored credentials)
  └── <script src="app.js?v=69">                  (manual cache-busting)
```

Backend (untouched by Phase 2; Phase 1 may extend RPC signatures per individual ticket needs):

```
supabase/
  ├── migrations/   (DB schema, RPCs get_session_list + get_filter_options, indexes)
  ├── functions/    (Deno Edge Functions: chat-feedback, invite-user)
  └── setup/        (RLS bootstrap for pre-existing tables)
```

### 1.2 Tech stack

| Layer | Technology | Notes |
|---|---|---|
| Frontend | Vanilla JS (ES2020+), HTML, CSS | No bundler, no transpiler, no framework |
| Frontend deps | `@supabase/supabase-js@2` via CDN | Single runtime dependency |
| Database | Supabase Postgres | `chat_messages`, `chat_feedback`, `chat_view_user_roles`, `visitors_settings` (pre-existing) |
| Server-side filtering | PL/pgSQL RPC functions | Two-stage `get_session_list` (well-designed); `get_filter_options` |
| Edge Functions | Deno / TypeScript | `chat-feedback` (deployed `--no-verify-jwt`), `invite-user` (admin-only with JWT verify) |
| Auth | Supabase Auth + Google OAuth | Per-environment `allowedDomains`; first-user-admin DB trigger |
| Tests | None | No test directory, no test runner |
| Build / CI | None | Manual `?v=N` cache-bust, manual Edge Function deploys |

### 1.3 Data flow

```
┌─────────────┐         RPC get_session_list (filters/cursor)         ┌───────────────────┐
│             │ ◄────────────────────────────────────────────────────►│                   │
│             │         RPC get_filter_options (login)                 │   Postgres        │
│             │ ◄────────────────────────────────────────────────────►│                   │
│             │         .from(chat_messages).select/eq                 │   - chat_messages │
│             │ ◄────────────────────────────────────────────────────►│   - visitors_     │
│  Browser    │         .from(visitors_settings).select/eq            │     settings      │
│  (app.js)   │ ◄────────────────────────────────────────────────────►│   - chat_view_    │
│             │         .from(chat_view_user_roles).select            │     user_roles    │
│             │ ◄────────────────────────────────────────────────────►│   - chat_feedback │
│             │         Realtime channel INSERT on chat_messages      │                   │
│             │ ◄────────────────────────────────────────────────────►│                   │
│             │         .functions.invoke(chat-feedback / invite-user)│   Edge Functions  │
│             │ ◄────────────────────────────────────────────────────►│                   │
└─────────────┘                                                        └───────────────────┘
```

Frontend surfaces (all in `app.js` + `index.html`):

- **Login panel** — env selector + Google OAuth.
- **Top nav bar** — burger menu, search input, filter button, env switcher, Live badge, refresh.
- **Filter popover** — date/msg-count/tools/categories/visitor/CRM filters (4 logical groups in HTML).
- **Session sidebar** — list (50 + infinite scroll), session metadata + badges.
- **Chat area** — message bubbles (human / AI / tool-call / tool-result / system).
- **Detail sidebar** — reviewed toggle, feedback button, in-session search, quick-jump, duration, classification badges, tools used, visitor info.
- **Feedback modal**, **Admin invite modal**, **Users modal**.

### 1.4 What the backend does well (and why it's the rewrite's contract)

- `get_session_list` uses a **two-stage architecture** ([create_session_rpc.sql:64-188](../../supabase/migrations/create_session_rpc.sql)): Stage 1 narrows to candidate session IDs via lightweight `GROUP BY`; Stage 2 extracts JSONB metadata + `visitors_settings` JOIN only for those candidates.
- AI metadata extraction tolerates **both wrapped and flat content formats** via `COALESCE(content->'output', content)`. Contract the rewrite has to honor.
- Edge Function `invite-user` verifies JWT, looks up the admin role through the service-role client, and gracefully handles already-existing users.
- Indexes are sensible: `idx_chat_messages_created_at`, `idx_chat_messages_session_id`, `idx_chat_messages_session_created`, `idx_visitors_settings_session_id`.

**Conclusion:** the backend is the load-bearing part of the system. The Vue rewrite consumes it via the same RPCs, Edge Functions, and Realtime channel.

## 3. The plan

### 3.1 Phase 1 — Ship the seven open tickets (≈1.5–2 weeks)

**Scope:** close `#148`, `#149`, `#150`, `#151`, `#153`, `#154`, `#155` in the existing vanilla `app.js` / `index.html`. Each ticket gets its own PR for reviewability and revertability. **No structural refactor; no cleanup of catalogue items from §2.** Backend RPC signatures may be extended where a specific ticket requires it (see §3.1.2 below) — the rewrite then inherits the extended signatures.

#### 3.1.2 Backend touches that Phase 1 may require

Phase 1 is **frontend-only by default**, but two tickets may need backend extension. Either is acceptable as long as the change is additive (new RPC parameters with defaults, not signature changes):

- **#155** — extend `get_session_list`'s `p_session_id` semantics to ILIKE-match `visitors_settings.request_id`, `lead_id`, `case_id`, `booking_identifier`. Or keep it client-side with extra `.eq()` round-trips. *D4 below.*
- **#149** — add `p_human_min/max`, `p_ai_min/max`, `p_tool_min/max`, `p_system_min/max` to `get_session_list`. Or keep filtering client-side on loaded sessions only. *D3 below.*

Whatever ships in Phase 1 becomes part of the rewrite's contract; the Vue version will target the post-Phase-1 backend shape.

#### 3.1.3 Out of scope for Phase 1

Everything in §2 (the structural catalogue) is **explicitly deferred to Phase 2**. That includes:

- Module split, data-access layer, single content parser (B5).
- Dead-code removal (B1 duplicate `buildSessionFromMessages`, B2 `logStatus` no-ops, B3 SVG dupes).
- N+1 visitor enrichment fix (D).
- Users modal `.limit()` / pagination (E).
- Single render path (F2 / F3).
- Build tooling / cache-busting (I1 / I2).
- Test infrastructure (J).

If during Phase 1 a ticket fix incidentally touches catalogue items (e.g. #150 might naturally clean up some duplicate visitor-rendering logic), do the minimal local cleanup but **don't expand scope**. The rewrite handles the rest.

### 3.2 Phase 2 — Vue 3 rewrite (≈3 weeks)

**Goal:** replace the frontend with a clean, typed, testable Vue 3 codebase. Backend untouched (working from the post-Phase-1 contract). Cutover when feature parity is reached.

#### 3.2.1 Stack

| Layer | Choice | Reason |
|---|---|---|
| Framework | **Vue 3 + Composition API + Single-File Components** | Decided. Composition API for typed reactive state; SFC `<style scoped>` replaces the 1,800-line inline `<style>` naturally. |
| Language | **TypeScript** (strict mode) | `chat_messages.message` JSON shape needs types; `@supabase/supabase-js` ships TS types; Vue 3 + TS is the canonical combination. |
| Build tool | **Vite** | Canonical for Vue 3; sub-second HMR; file-hash cache-busting kills the `?v=N` problem. |
| State | **Pinia** | Canonical Vue 3 store; replaces the current globals (`allSessions`, `filtersApplied`, `currentFilterCriteria`, etc.) with typed stores. |
| Routing | **Vue Router** | Two routes (`/login`, `/app`) but the env+session deep-link logic benefits from explicit route guards. |
| Styling | **SFC `<style scoped>`** | Each component owns its CSS. Keep the existing CSS custom properties (`--accent`, `--shadow-sm`, badge palette) in a small `src/styles/tokens.css`. |
| Supabase client | **`@supabase/supabase-js@2`** as an npm dep (not CDN) | Pinned version, types, tree-shaking. |
| Tests | **Vitest** (unit) + **Playwright** (e2e) | Vitest is the natural pair for Vite/Vue. Playwright for the OAuth + realtime smoke. |
| Lint / format | **ESLint + Prettier** + `vue-tsc` for type-checking | Standard for the stack. |

#### 3.2.4 Cutover strategy

1. Both versions deployed to separate URLs against the same Supabase environments. The Vue version reads/writes the same tables, hits the same RPCs, invokes the same Edge Functions. No data migration needed.
2. Internal soak: Peter + one other reviewer use the new URL exclusively for a week. Issues filed against the rewrite, not patched in the legacy.
3. Swap: primary URL points at the Vue bundle. Legacy stays reachable at an `/legacy/` path for one release cycle.
4. Retire: legacy moved to `legacy/` subfolder in the repo, `app.js`/`index.html` deleted from root after one quiet week.

If the rewrite hits a blocker, the cutover doesn't happen — the legacy keeps running, and the Vue branch holds for repair.
